STREAMFLIX ADMIN MOVIE UPLOAD GOAL
Date: 2026-10-17

GOAL

Build a reliable admin publishing flow in which every entered field and every
selected media file is stored in Supabase, the published catalog item always
opens its own uploaded video, and TMDB is optional reference metadata rather
than the identity or playback source of the movie.

CORE IDENTITY DECISION

1. public.content.content_id is the canonical StreamFlix identity everywhere.
2. tmdb_id is optional external metadata. It must never replace content_id.
3. A TMDB ID may be stored only after the admin explicitly selects an exact
   TMDB search result. Never infer it from a title or from content_id.
4. Playback, subtitles, comments, reactions, watch history, soundtracks,
   notifications, and admin links must use content_id.
5. TMDB-only features such as trailers and TV episode metadata may use tmdb_id
   when it exists. When it does not exist, those features must be unavailable
   gracefully instead of using content_id as a fake TMDB ID.

CURRENT PROBLEMS TO REMOVE

1. The admin file controls do not upload video or subtitle bytes. They save only
   the selected filenames.
2. Thumbnail files are converted to base64 and stored directly in the content
   table instead of Supabase Storage.
3. Admin-created rows receive catalog_source='manual' and tmdb_id=NULL.
4. The viewer catalog filters out every row whose tmdb_id is NULL.
5. Show.id currently mixes TMDB IDs and content IDs, allowing an internal ID to
   be sent to TMDB accidentally.
6. Playback uses shared static demo videos selected by quality instead of the
   uploaded content.video_file.
7. Subtitle and engagement resolution look up content through tmdb_id.
8. The Add Content modal closes and reports success without awaiting the insert,
   so a failed request can look successful.
9. Content insertion and genre insertion are separate operations and can leave a
   partially-created record.
10. The TMDB catalog sync upserts video_file=NULL and subtitle=NULL. If a manual
    upload shares its TMDB ID, a later sync could overwrite curated data unless
    the sync rules are changed first.

TARGET ADMIN FLOW

1. The admin opens Add Content and chooses Movie or TV Series.
2. The admin optionally searches TMDB through a server-side Edge Function.
3. Selecting a TMDB result records the exact tmdb_id and media type and may
   prefill title, synopsis, year, runtime, rating, genres, and artwork.
4. The admin can review and edit every prefilled value before publishing.
5. The admin selects a thumbnail, required video, and optional subtitle file.
6. StreamFlix validates fields, file types, file sizes, category/TMDB media-type
   consistency, and duplicate TMDB references.
7. Supabase creates an unavailable draft content row and returns content_id.
8. The browser uploads the actual files to deterministic Storage paths scoped by
   content_id. Large video bytes go directly to Storage and never through an
   Edge Function request body.
9. After all required uploads succeed, a database operation stores the object
   paths, genres, metadata, and requested availability state.
10. The title becomes visible only after the required database record and video
    object both exist.
11. The success toast and modal close occur only after the entire publish action
    succeeds.
12. Selecting Play loads a signed URL for that row's video_file and never falls
    back to an unrelated TMDB or demo movie.

CONTENT DATA CONTRACT

Keep and correctly populate these public.content fields:

- content_id: canonical StreamFlix ID generated by Supabase
- category_id: selected Movie or TV Series category
- title: required admin-reviewed title
- synopsis: required description
- release_year: validated year
- runtime: validated minutes
- age_rating: required rating
- thumbnail: Storage object path, not base64 content
- video_file: private Storage object path for the uploaded movie
- subtitle: private Storage object path or NULL
- total_streams_count: server-owned counter starting at zero
- availability_status: unavailable while staging, then the admin's selected state
- tmdb_id: exact optional TMDB reference
- popularity_rank: optional and normally NULL for manual uploads
- catalog_source: manual for admin-curated records, including records linked to
  TMDB; tmdb only for rows owned by the automated TMDB catalog sync
- synced_at: used only for automated TMDB synchronization
- admin_updated_at: maintained by the existing database trigger

Add an explicit publishing state if availability_status cannot safely represent
the upload lifecycle:

- publishing_status: draft, uploading, ready, failed

Do not mark a row available unless publishing_status is ready and video_file is
present.

FRONTEND ID MODEL

Replace the overloaded Show.id contract with explicit identities:

- contentId: required number from public.content.content_id
- tmdbId: optional number from public.content.tmdb_id
- id: remove where practical, or temporarily make it an alias of contentId only

Update all callers so:

- navigation and playback pass contentId
- engagement uses contentId directly
- subtitle loading uses contentId directly
- soundtrack and refresher loading use contentId directly
- watch history uses contentId directly
- notification clicks pass contentId and preserve tmdbId separately
- TMDB trailer and TV episode requests require tmdbId
- no code uses `tmdb_id ?? content_id` as a generic external identifier

SUPABASE STORAGE DESIGN

Use purpose-specific buckets or the existing equivalent buckets with these
security properties:

1. content-thumbnails
   - Artwork only.
   - Public delivery is acceptable if the product intentionally exposes catalog
     artwork; otherwise use signed URLs.
2. video_file or content-videos
   - Private.
   - Authenticated active subscribers may read published content.
   - Only authorized content admins may insert, update, or delete objects.
3. subtitle
   - Private.
   - Authenticated active subscribers may read published content.
   - Only authorized content admins may insert, update, or delete objects.

Use deterministic paths:

- content/{content_id}/thumbnail/{sanitized-filename}
- content/{content_id}/video/{sanitized-filename}
- content/{content_id}/subtitle/{sanitized-filename}

Enforce bucket MIME-type and size limits. Validate the detected MIME type as
well as the filename extension. Never allow clients to choose an arbitrary path
outside their content_id prefix.

DATABASE AND RLS STEPS

1. Add publishing_status and any required asset metadata columns through a
   migration if the existing fields are insufficient.
2. Add checks requiring supported status values and valid metadata.
3. Keep the unique (category_id, tmdb_id) constraint for non-null TMDB IDs.
4. Add an authenticated admin RPC to create the draft metadata and genre links
   atomically and return content_id.
5. Add an authenticated admin RPC to finalize publishing only after required
   Storage object paths are supplied.
6. Make RPCs verify the caller's current admin role server-side.
7. Make total_streams_count, catalog_source, synced_at, and audit timestamps
   server-owned rather than accepting arbitrary client values.
8. Align content and content_genre policies so every admin role allowed to create
   content can complete the genre assignment.
9. Keep public catalog reads limited to available, fully-published records.
10. Add cleanup for abandoned draft rows and orphaned Storage objects.

TMDB REFERENCE FLOW

1. Create an authenticated server-side TMDB search Edge Function. Keep the TMDB
   API key in Supabase secrets and never expose it to the browser.
2. Accept a normalized search query and media type with strict length limits.
3. Return only the fields needed by the admin selection UI.
4. Display TMDB title, year, poster, media type, and tmdb_id so the admin chooses
   the exact result.
5. Store the chosen tmdb_id separately from content_id.
6. Allow publishing without a TMDB match.
7. Reject category/media-type mismatches and duplicate explicit references.
8. Never match automatically by title because remakes and identical names exist.
9. Never use TMDB video URLs as the StreamFlix playback source.

TMDB SYNC SAFETY

Change sync-tmdb-catalog before allowing linked manual uploads:

1. Automated synchronization may update only rows with catalog_source='tmdb'.
2. A manual row sharing a TMDB ID must never have title, thumbnail, video_file,
   subtitle, availability, genres, or admin edits overwritten by the sync.
3. TMDB refresh payloads must not write video_file or subtitle at all.
4. Stale cleanup must continue deleting only catalog_source='tmdb' rows.
5. If a TMDB import collides with a manual linked record, skip it and report the
   collision in the sync result instead of modifying the manual row.
6. Add regression tests proving that a catalog sync preserves uploaded assets.

ADMIN FORM IMPLEMENTATION

1. Add an optional Find on TMDB control and a clear-link action.
2. Keep all current metadata fields visible after TMDB selection.
3. Show the selected TMDB ID and media type as read-only reference data.
4. Store actual File objects for thumbnail, video, and subtitle until submission.
5. Require a video for new published content.
6. Show per-file validation, upload progress, and retry behavior.
7. Await create, upload, finalize, and reload before showing success.
8. Keep the modal open and show the real failure when any stage fails.
9. On edit, preserve existing asset paths unless a replacement file is selected.
10. Delete replaced objects only after the database points to the new object.
11. On a failed new upload, remove uploaded objects and retain or mark the draft
    failed so an admin can retry safely.

VIEWER CATALOG AND PLAYBACK STEPS

1. Remove the `.not('tmdb_id', 'is', null)` catalog filter.
2. Query content_id, tmdb_id, video_file, subtitle, and publishing state.
3. Include all available, fully-published manual and TMDB-linked records.
4. Map content_id and tmdb_id to separate Show properties.
5. Add a playback loader that fetches the content row by content_id.
6. Confirm the row is available and the viewer has an active subscription.
7. Create a short-lived signed URL for video_file.
8. Use that signed URL as the video element source.
9. Do not use PLAYBACK_SOURCE_BY_QUALITY for uploaded titles. Until transcoding
   exists, show only the quality of the uploaded source or label it Auto.
10. Load subtitles by content_id and sign the stored subtitle object path.
11. Load comments, reactions, soundtracks, refreshers, and history directly with
    content_id.
12. Use tmdbId only for optional TMDB trailers, episode metadata, or enrichment.

SEARCH AND NOTIFICATION BEHAVIOR

1. Search the local Supabase catalog so manual titles without TMDB IDs are
   discoverable.
2. TMDB search results are marked available only when an available local content
   row has the same explicit tmdb_id and media type.
3. Notification records carry contentId and optional tmdbId separately.
4. Clicking an admin-content notification opens the local content row by
   contentId.
5. A missing tmdbId must never make a valid uploaded movie unplayable.

DELETE AND REPLACEMENT BEHAVIOR

1. Resolve and verify the exact database row before deletion.
2. Delete or archive dependent database records according to existing retention
   rules.
3. Delete Storage objects only after authorization and exact-path validation.
4. Report partial cleanup failures for administrator retry.
5. Never delete a whole bucket or another content item's prefix.

TEST PLAN

1. Add a movie with every field and confirm every value is stored correctly.
2. Confirm thumbnail, video, and subtitle bytes exist in their Storage buckets.
3. Confirm the success toast appears only after finalization.
4. Publish without TMDB and confirm the title appears, opens, and plays its own
   uploaded video.
5. Publish with an explicitly selected TMDB result and confirm contentId remains
   the internal identity while tmdbId is used only for enrichment.
6. Confirm two same-title movies cannot be confused through title matching.
7. Confirm internal contentId is never sent to a TMDB endpoint.
8. Confirm a missing video prevents an available/published state.
9. Confirm subtitles load from the uploaded subtitle object using contentId.
10. Confirm comments, reactions, history, soundtrack, and notifications use the
    correct content row.
11. Confirm Search finds a manual movie with tmdb_id=NULL.
12. Run TMDB sync and prove it does not overwrite or delete a manual upload.
13. Confirm a failed upload remains unavailable and can be retried.
14. Confirm replacing an asset preserves the old working asset until finalization.
15. Confirm unauthorized users cannot upload, replace, publish, or delete media.
16. Confirm active subscribers can read signed media URLs and inactive users
    cannot.
17. Test large video upload progress, cancellation, retry, and expired signed URLs.
18. Run formatting, focused catalog/admin/playback tests, the full regression
    suite, and a production build before deployment.

IMPLEMENTATION ORDER

1. Add explicit contentId/tmdbId types and trace every current Show.id consumer.
2. Create database migration, RPCs, Storage buckets, and RLS policies.
3. Protect manual records from sync-tmdb-catalog overwrites.
4. Implement server-side TMDB search and exact-selection UI.
5. Implement draft creation and real Storage uploads in the admin form.
6. Implement publish finalization and failure cleanup.
7. Update catalog queries to include published manual content.
8. Replace static playback with the uploaded video's signed URL.
9. Convert subtitles and engagement to contentId lookups.
10. Update search and notification navigation.
11. Add automated tests and perform a real admin upload in a test environment.
12. Inspect the stored row, Storage objects, playback request, and related records.
13. Deploy migrations and Edge Functions before releasing the frontend.

ACCEPTANCE CRITERIA

The goal is complete only when an authorized admin can publish a movie with all
entered fields and real files, a subscriber can find it and play the exact
uploaded video, every related feature uses the same public.content.content_id,
TMDB linkage is explicit and optional, and running the TMDB sync cannot overwrite
or redirect the manually uploaded movie.

ROLLBACK

If publishing fails after release, disable final publication while preserving
draft rows and uploaded objects for recovery. Do not restore content_id-to-TMDB
fallback behavior and do not silently substitute shared demo playback media.
